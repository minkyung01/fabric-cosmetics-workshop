# 07. Purview 거버넌스 — 민감도 레이블 적용과 정책 확인

[목차](../README.md) \| 이전: [06. SQL Serving DB](06-serving-db.md) \| 다음: [08. Data Highway 2.0 논의](08-discussion.md)

에이전트가 연구 데이터를 읽고 업무 DB까지 연결하면 **무엇을 분류하고 어디까지 제공할지** 결정해야 합니다. 참가자가 직접 레이블을 적용하는 기본 실습과, 준비된 정책·카탈로그를 활용하는 확장 실습을 구분합니다. 참가자가 Purview 관리자가 되거나 테넌트 정책을 새로 만들 필요는 없습니다.

## 시작 전 확인

| 범위 | 관리자 사전 준비 | 참가자 조건 |
|---|---|---|
| **기본: 레이블 적용** | 정보 보호 설정, 레이블 생성·참가자 그룹에 게시, 필요한 라이선스 확인 | **Pro 또는 PPU**, 항목 편집 권한, 해당 레이블 사용 권한 |
| **확장 A: DLP 정책 팁** | 지원 라이선스·관리 역할, 실습 작업 영역만 대상으로 하는 정책, 사전 평가 확인 | 실습 항목 접근. 상세 확인·응답은 항목 소유자에 해당하는 **Admin/Member** 계정으로 사전 점검 |
| **확장 B: 카탈로그 검색** | Purview 연결·스캔 완료, 검색·자산 읽기 권한 부여 | 준비된 카탈로그 자산에 대한 읽기 권한 |

**현실적인 운영 범위:** 레이블 생성·게시와 정책 반영은 미리 끝내고, 수업에서는 레이블 적용을 수행합니다. DLP 신규 테넌트 온보딩은 몇 시간이 걸릴 수 있고 스캔·정책 평가도 비동기이므로 “실습 중 정책을 처음 만들고 즉시 탐지”를 완료 조건으로 삼지 않습니다. 권한·라이선스를 준비하지 못한 경우에는 이 장의 분류 설계만 수행하며 실제 적용 완료로 표시하지 않습니다. 자세한 준비는 [관리자 가이드](../admin/README.md)를 봅니다.

## 1. 무엇이 민감한가

| 데이터 | 예 | 민감도 |
|---|---|---|
| 처방 배합비 | `formula_line.pct_wt` | 영업 비밀 — 가장 높음 |
| 개발 과제·안정성 시험 | `dev_project`, `stability_test` | 사내 기밀 |
| 공급사·단가 | `supplier`, `raw_material.unit_price_krw` | 사내 기밀 |
| 검토 요청·조치 이력 | `ops.review_request`, `ops.action_log`, `serving.review_request` | 사내 업무 데이터 — 원료·미출시 과제·사용자 식별자가 포함되므로 조직 정책에 따라 분류 |

**확인할 결과:** `lh_cos`에는 배합비가 있고 SQL DB에는 검토에 필요한 일부 정보만 게시된다는 차이를 설명합니다. 배합비의 숫자만으로 DLP가 영업 비밀을 자동 인식한다고 가정하지 않습니다.

## 2. 게시된 민감도 레이블 직접 적용

1. 작업 영역에서 `lh_cos`를 열고 현재 민감도 표시를 확인합니다.
2. 항목 머리글의 민감도 메뉴 또는 **Settings → Sensitivity label**을 엽니다.
3. 관리자가 안내한 실습용 레이블(예: `Caldova-R&D-Confidential`)을 선택하고 저장합니다. 레이블 이름은 조직마다 다를 수 있습니다.
4. 항목을 다시 열고 레이블이 유지되는지 확인합니다.
5. 06장을 진행했다면 `sqldb_cos`도 열어 관리자가 지정한 업무 데이터 레이블을 적용합니다. 원본의 레이블이 SQL로 자동 복사된다고 가정하지 않습니다.

**확인할 결과:** `lh_cos`의 레이블 이름을 확인하고, 적용 이유를 `formula_line.pct_wt`와 연결해 설명합니다. 이는 항목 단위 레이블이며 특정 열 하나에 별도 권한을 설정한 것이 아닙니다. 지원되는 내보내기·상속 동작만 별도로 확인하고 모든 출력·복사본에 보호가 자동 전파된다고 설명하지 않습니다.

## 3. DLP 정책 팁 확인 (준비된 환경의 확장 A)

1. 관리자가 알려 준 정책 대상과 조건을 확인합니다. 위치는 **Fabric and Power BI workspaces**, 대상은 실습 작업 영역, 조건은 실습 레이블입니다.
2. 데이터 변경에 따른 평가가 미리 확인된 `lh_cos`를 열고 정책 위반 표시에서 **Show full details / View all**을 엽니다. 정책이 새 레이블·데이터를 평가하는 데 시간이 걸리면 준비된 평가 결과 항목을 사용합니다.
3. 정책 이름·감지 조건·정책 팁을 읽고 어떤 행동을 요구하는지 확인합니다.
4. 처방 배합비가 왜 기밀인지, 정책이 어떤 레이블을 근거로 매치했는지 구분해 설명합니다.

**확인할 결과:** 정책 팁에서 실습 정책과 근거를 확인합니다. 정책 우회·오탐 신고는 연습 삼아 실행하지 않습니다. 이 실습은 **알림·관찰용 정책**을 사용하고 접근 차단은 설정하지 않습니다.

DLP 상세 화면을 볼 수 없는 참가자는 관리자와 함께 확인합니다. 확장 A를 못 끝내도 레이블 적용 기본 실습의 완료 여부와 구분해 기록합니다.

## 4. 카탈로그에서 자산 찾기 (준비된 환경의 확장 B)

1. 관리자가 제공한 Purview **Unified Catalog**에서 `lh_cos`를 검색합니다.
2. 실제 스캔된 테이블 자산과 원본을 열어 소유자·설명·분류 중 준비된 항목을 확인합니다.
3. 같은 자산을 다른 참가자도 찾아볼 수 있도록 식별 정보와 데이터 원본을 확인합니다.

**확인할 결과:** Fabric에서 데이터를 읽는 권한, 카탈로그에서 메타데이터를 검색하는 권한, 레이블·DLP 정책을 관리하는 권한이 서로 다름을 설명합니다. 이 단계는 Microsoft Purview Data Map/Unified Catalog 연결이 필요한 별도 준비이며, 레이블 적용만을 위해 카탈로그 스캔을 구성할 필요는 없습니다.

## 꼭 구분할 것

- **Lineage(계보) 화면은 Fabric 기능입니다.** Purview 자체 기능처럼 설명하지 않습니다.
- **Ontology의 업무 정의와 민감도 레이블은 데이터 접근 권한 자체가 아닙니다.** 실제 접근은 작업 영역·항목·SQL/OneLake 보안으로 통제합니다. 지원되는 DLP 제한 동작은 정책에 따라 별도로 적용됩니다.
- 승인된 Operations agent 작업은 **작성자 권한**으로 실행됩니다. 작성자 권한을 최소로 두는 것도 거버넌스입니다.

## 이 장의 완료 기준

- **기본:** `lh_cos`에 지정된 레이블을 직접 적용하고 재열기 후 확인했습니다.
- **기본:** SQL Serving으로 전달한 정보와 배합비 원본의 분류 차이, 레이블과 접근 통제의 차이를 설명할 수 있습니다.
- **확장(환경 조건부):** DLP 정책 팁·근거 또는 카탈로그 자산을 확인하고, 수행한 범위를 구분했습니다.

## Troubleshooting

- 레이블 메뉴가 없거나 회색이면 **Pro/PPU·편집 권한·레이블 게시 대상·테넌트 설정**을 관리자와 확인합니다.
- DLP 팁이 없으면 정책 위치·작업 영역 포함 여부·라이선스·평가 완료 여부를 확인합니다. 기본 Contributor 권한만으로 소유자용 응답 화면이 보인다고 가정하지 않습니다.
- 카탈로그 검색이 안 되면 스캔 완료와 자산 읽기 권한을 확인합니다. 카탈로그 권한을 주기 위해 참가자에게 전체 보안 관리 역할을 주지 않습니다.
