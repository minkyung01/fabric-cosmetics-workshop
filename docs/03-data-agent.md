# 03. Data Agent — 업무 맥락으로 다양한 질문 검증하기

[목차](../README.md) \| 이전: [02. Graph](02-graph.md) \| 다음: [04. Operations Agent](04-operations-agent.md)

앞에서 만든 업무 모델로 **대조·규칙·용어·관계·What-if·여러 데이터 통합** 질문에 답해 봅니다. 단순히 대상 목록을 맞히는 데서 끝나지 않고, **어떤 의미·조건·경로로 답했는지와 어디까지 판단할 수 있는지**를 검증합니다. 기본 경로는 **Ontology 업무 맥락 → Lakehouse SQL**입니다. Ontology 자체가 질의 실행 엔드포인트이거나 Graph 저장소인 것은 아닙니다. 별도 Graph model을 연결하면 GQL 질의와도 비교할 수 있습니다.

01장에서 사용한 **Ontology Agent의 Plan 모드도 모델 설명과 데이터 질의에 답할 수 있습니다.** 이번 장에서는 Ontology 편집 화면의 대화가 아니라, **별도 Data Agent 항목**에 같은 Ontology 문맥과 원본을 연결해 질문하는 경험을 구성합니다.

## 시작 전 확인

- 1장에서 `ont_cos`의 관계와 속성을 완성했고, `lh_cos`의 SQL analytics endpoint에서 `gold` 테이블을 조회할 수 있습니다. Graph는 필수가 아닙니다.
- 테넌트에서 Data agent와 Copilot·Azure OpenAI 설정이 켜져 있어야 합니다(관리자 준비 사항).
- Data agent 하나에 데이터 원본은 최대 5개까지 연결할 수 있습니다.
- 질문은 **핵심 11개 테이블·9개 엔터티**로 풉니다. 여기서 여러 데이터 통합은 같은 Lakehouse 안의 발주·공급사·처방·제품·계획·시험 데이터를 조인하는 뜻이며, 별도 시스템 간 교차 원본 질의나 07장 이후 엔터티 확장을 요구하지 않습니다.
- 날짜 계산의 기준일은 **2026-11-02**, 기본 QC 리드타임은 **7일**입니다. 질문에 제시한 입고일·QC 일수는 **조회용 가정**이며 04장의 실제 지연 반영을 먼저 실행하지 않습니다. 이전 실습으로 원본이 바뀌었다면 현재 ETA와 가정 ETA를 구분합니다.

## 1. Data Agent 만들고 원본 연결

1. 작업 영역에서 **+ New item** → **Data agent**를 고르고 이름을 `da_cos`로 만듭니다.
2. **Sources → Add sources → Add an ontology**(환경에 따라 **Add data source**)에서 `ont_cos`를 추가합니다. 새 Ontology 문맥 경험은 **preview runtime**을 사전에 확인합니다.
3. Ontology를 펼쳐 엔터티와 연결된 원본 `lh_cos`를 확인합니다. 필요하면 연결 가능한 Lakehouse 원본을 추가/마운트해 원본별 지침·예제 SQL을 설정합니다. 요청 사용자에게 Lakehouse/SQL endpoint 읽기 권한이 있어야 합니다.
4. **선택:** 02장을 수행했다면 Graph model `ont_cos_graph_…`을 추가합니다. SQL과 GQL을 구분해서 비교하려면 별도의 `da_cos_graph`를 만들고 Graph 원본만 연결하는 편이 명확합니다.

**확인할 결과:** Sources에서 `ont_cos`와 연결된 Lakehouse 원본을 확인하고, 기본 질문의 실행 단계에 **SQL과 실제 Lakehouse 실행 원본**이 표시됩니다. Graph를 만들지 않아도 이 단계가 동작합니다. Ontology 편집 후 문맥은 자동 반영에 최대 10분이 걸릴 수 있으므로 **Refresh**로 갱신합니다.

## 2. 에이전트 지침 입력

**Agent instructions**에 아래 지침을 붙여 넣습니다.

``` text
Caldova 코스메틱 연구소의 원료 변경 영향 분석을 돕습니다. 답은 한국어로 씁니다.
기본 질의는 ont_cos의 정의와 바인딩을 참고해 lh_cos의 gold 테이블에 SQL로 실행합니다.
관계 이름은 업무 의미이며 SQL 테이블명과 같다고 가정하지 않습니다.

용어
- 성분(Ingredient)과 원료(RawMaterial)는 다릅니다. 공급 지연은 원료 코드(material_code) 단위로 판단합니다.
- 처방 버전(FormulaVersion)의 status는 현행·개발중·폐기입니다. is_active = true인 버전만 영향 분석 대상입니다.
- 처방 버전의 활성 여부, 대체 원료의 approval_status, CN 등록 상태는 서로 다른 판단 기준입니다. 같은 성분이라는 이유로 대체 가능하거나 같은 공급사의 원료가 모두 지연된다고 단정하지 않습니다.

영향 대상 찾기
- 원료 → 처방 버전(uses_material) → 제품(made_with) → 생산 계획(produces), 처방 버전 → 안정성 시험(tests_version) → 개발 과제(for_project) 경로를 따라갑니다.
- 예정 상태의 안정성 시험만 계산합니다. 원료 필요일 = 생산 계획일 또는 안정성 시험 배치일 − QC 리드타임입니다.
- 기본 QC는 7일이며 질문에 다른 일수가 명시되면 해당 가정으로 다시 계산합니다. 여유일 = 필요일 − 입고일이고, 여유일 < 0만 영향 대상입니다. 0일은 일정 기준 영향 없음입니다.
- 대체 후보는 alternative_to 관계로 찾습니다. 비교 질문에는 승인·검토중 후보를 모두 보여 주되, 제안할 때는 approval_status = '승인', 필요일 이내 입고, CN 제품의 cn_registration = '완료'를 각각 확인합니다.
- 대체 발주 가정일은 2026-11-02이고 예상 입고일은 가정 발주일 + 후보 원료의 lead_time_days입니다. 후보라는 사실을 품질·공정 검증 완료나 사용 승인으로 확대하지 않습니다.

가정과 데이터 범위
- 현재 발주의 ETA와 질문에 명시된 가정 ETA를 구분합니다. What-if는 원본·Ontology·ops 테이블을 변경하지 않는 계산입니다.
- 여러 조건을 비교할 때는 대상·원료·날짜 기준을 고정하고 바뀐 조건만 달리합니다.
- 시험에 제품 시장이 연결되지 않으면 시장을 추정하지 않습니다.
- 원료 단가와 생산 계획 수량만으로 총 추가 비용·생산 가능 수량을 확정하지 않습니다. 농도·제형 환산, 소요량·재고 할당·공정 검증 등 부족한 근거를 구분합니다.

답변 원칙
- 대상의 ID·이름과 포함·제외 이유를 표로 보여 줍니다. 계산 질문에는 기준일·가정·필요일·여유일·판정을 함께 표시합니다.
- 용어는 Ontology 정의와 실제 열을 구분해 설명하고, 관계 질문은 중간 엔터티·ID와 저장된 관계 방향을 밝힙니다.
- 어떤 원본·조인·필터로 찾았는지 설명하고 실행한 SQL 또는 GQL을 확인할 수 있게 합니다.
- 확인할 수 없는 값은 추측하지 말고 확인할 수 없다고 말합니다.
- 구매 발주나 처방을 바꾸라고 단정하지 말고 '검토 필요'로 제안합니다.
```

문항별로 **답과 필수 근거 충족 / 일부 누락 / 불일치·확인 불가**를 기록합니다. 최초 답과 실행 질의를 남기고, 답이 다르면 조인·활성 필터·가정 날짜·QC·경계 조건을 확인해 다시 질문합니다. 보완 질문 뒤의 답은 별도로 기록합니다.

**확인할 결과:** 유형마다 두 문항의 결과와 차이의 원인을 설명할 수 있습니다. 특히 DA03의 0일 경계, DA04의 세 조건, DA09–DA10의 바뀐 변수, DA12의 판단 한계를 확인합니다.

선택 Graph 에이전트에서는 같은 문항의 생성 GQL·실제 투영 범위와 결과를 비교합니다. 대체 승인 상태처럼 Graph 관계에 투영되지 않은 값은 확인 불가로 기록하고 Lakehouse SQL로 검증합니다. 한 에이전트에 두 원본을 넣고 항상 원하는 쪽으로 라우팅될 것이라고 가정하지 않습니다.

> **토론 포인트:** Data Agent는 "내가 궁금한 것을 질문"할 때 강력합니다. 하지만 매번 사람이 물어야 합니다. 공급 지연처럼 **정해진 조건**은 사람이 묻기 전에 알려 주는 편이 낫습니다 — 다음 장의 Operations Agent입니다.

## 이 장의 완료 기준

- `da_cos`가 Ontology 문맥을 활용해 Lakehouse에 SQL 질의하는 경로를 확인했습니다. Graph는 선택 비교입니다.
- 6개 유형·12문항의 답과 근거를 정답 기준·Notebook과 대조하고, 누락·불일치·확인 불가를 구분했습니다.
- 날짜·QC 가정을 바꾼 계산과 실제 원본 변경을 구분하고, 데이터만으로 확정할 수 없는 결론을 설명할 수 있습니다.

## Troubleshooting

- Graph model이 원본 목록에 보이지 않으면 Graph의 미리 보기 기능 설정을 관리자에게 확인하고, Ontology만으로 진행합니다.
- "데이터에 접근할 수 없다"는 답이 나오면 `lh_cos` 읽기 권한과 Ontology 원본 바인딩을 확인합니다.
- 답이 지침과 다르게 폐기 버전을 포함하면 질문에 `is_active가 true인 버전만`을 덧붙여 다시 묻고, 지침의 문장이 저장되었는지 확인합니다.
- 엔터티 정의가 오래되면 Ontology 문맥 **Refresh**를 실행하고 내려받은 문맥·실행 단계를 확인합니다. 문맥 편집은 Ontology에서 합니다.
- Ontology 내부의 일부 엔터티만 선택해 Data Agent에 노출하는 기능은 현재 지원되지 않습니다. 기본 과정에서는 01장에서 완성한 핵심 `ont_cos`를 사용합니다.
